ในบางกรณี เราอาจต้องนำไฟล์เข้าไปยัง PersistentVolumeClaim (PVC) เช่น การ Restore Backup, Seed Data หรือย้ายข้อมูล โดยไม่ต้องการแก้ไข Container Image หรือ Deployment ของแอปพลิเคชัน

วิธีหนึ่งคือสร้าง Pod ชั่วคราวขึ้นมาเพื่อ Mount PVC ที่ต้องการ จากนั้นใช้ `kubectl cp` หรือ `kubectl exec` เพื่อคัดลอกไฟล์ผ่าน Pod ดังกล่าว

บทความนี้จะทดลองทำ POC ด้วย BusyBox โดยแบ่งเป็นสองกรณี ได้แก่ การคัดลอกไฟล์ระหว่าง Local กับ PVC และการคัดลอกไฟล์ระหว่าง PVC โดยตรง

## 1. Copy ไฟล์จาก Local เข้า PVC

เริ่มจากกรณีที่ง่ายที่สุด สมมติว่าเรามีไฟล์ Backup หรือ Seed Data อยู่บนเครื่อง Local และต้องการนำไฟล์เหล่านั้นเข้าไปยัง PVC ของแอปพลิเคชัน

เราไม่จำเป็นต้องแก้ Deployment หรือเข้าไปยุ่งกับ Container ของแอปโดยตรง เพียงสร้าง BusyBox Pod ขึ้นมาหนึ่งตัวเพื่อ Mount PVC แล้วใช้ Pod นี้เป็นตัวกลางในการคัดลอกไฟล์

### เตรียม PVC ก่อนคัดลอก

ก่อนเริ่ม ควรตรวจสอบว่า PVC ที่ต้องการใช้งานอยู่ในสถานะ `Bound`

```bash
kubectl -n <namespace> get pvc
```

หาก PVC กำลังถูกใช้งานโดยแอปพลิเคชันอยู่ แนะนำให้ Scale Down แอปก่อน Restore หรือคัดลอกไฟล์ที่อาจกระทบข้อมูลเดิม เพื่อป้องกันการอ่านหรือเขียนไฟล์พร้อมกันระหว่างแอปกับ BusyBox

นอกจากนี้ หาก PVC เป็นแบบ `ReadWriteOnce` (RWO) และ BusyBox ถูก Schedule ไปคนละ Node กับแอป อาจเกิดปัญหา Multi-Attach ทำให้ไม่สามารถ Mount Volume ได้

สำหรับ POC นี้ เราจะ Scale Down แอปก่อนเริ่มทดลอง

```bash
kubectl -n <namespace> scale \
  deploy/<deployment> --replicas=0
```

รอให้ Pod ของแอปหยุดทำงานเรียบร้อยก่อนดำเนินการต่อ โดยต้องตรวจสอบด้วยว่าไม่มี Pod หรือ Job อื่นกำลังเขียนข้อมูลลง PVC เดียวกัน

<ChatMessage message="RWO ไม่ได้หมายความว่า PVC จะถูกใช้งานได้เพียง Pod เดียว แต่จำกัดการ Mount แบบ Read-Write ไว้ที่ Node เดียว การ Scale Down ในตัวอย่างนี้จึงช่วยทั้งเรื่องการเข้าถึง Volume และลดความเสี่ยงจากการเขียนข้อมูลพร้อมกัน" avatarKey="blackCat" />

### สร้าง BusyBox Helper Pod

สร้างไฟล์ `volume-copy-helper.yaml` โดยกำหนด `namespace` และ `claimName` ให้ตรงกับ PVC ที่ต้องการ

```yaml
# volume-copy-helper.yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox-helper
  namespace: <namespace>
  labels:
    app: volume-copy-helper
spec:
  restartPolicy: Never
  containers:
    - name: busybox
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: <pvc-name>
```

ในตัวอย่างนี้ เรา Mount PVC ไว้ที่ `/data` ภายใน BusyBox ดังนั้นไฟล์ที่เขียนลงใน Directory นี้จะถูกจัดเก็บอยู่ใน Volume ที่เชื่อมกับ PVC

Apply Manifest แล้วรอจน Pod พร้อมใช้งาน

```bash
kubectl apply -f volume-copy-helper.yaml

kubectl -n <namespace> wait \
  --for=condition=Ready \
  pod/busybox-helper \
  --timeout=60s
```

ลองตรวจสอบไฟล์ที่มีอยู่ภายใน Volume ก่อนคัดลอก

```bash
kubectl -n <namespace> exec busybox-helper -- ls -la /data
```

### คัดลอกไฟล์เข้า PVC

เมื่อ BusyBox พร้อมแล้ว เราสามารถใช้ `kubectl cp` เพื่อคัดลอกไฟล์จากเครื่อง Local เข้าไปยัง `/data` ได้ทันที

```bash
kubectl -n <namespace> cp \
  ./backup/. \
  busybox-helper:/data/
```

คำสั่งนี้จะคัดลอกเนื้อหาภายใน Directory `backup` จากเครื่อง Local เข้าไปยัง `/data` ของ BusyBox ซึ่งก็คือ PVC ที่เรา Mount ไว้นั่นเอง

หลังคัดลอกเสร็จ สามารถตรวจสอบไฟล์ปลายทางได้ด้วยคำสั่ง

```bash
kubectl -n <namespace> exec busybox-helper -- ls -la /data
```

การคัดลอกด้วย `kubectl cp` จะเขียนไฟล์ลงปลายทาง แต่ไม่ได้ลบไฟล์เก่าที่ไม่มีอยู่ใน Backup ดังนั้นหากต้องการ Restore ข้อมูลทั้ง Directory ให้กลับไปเป็นสถานะเดิม ควรตรวจสอบและจัดการข้อมูลปลายทางให้เหมาะสมก่อน

### Tip: Backup ไฟล์จาก PVC กลับมา Local

นอกจากการคัดลอกไฟล์เข้า PVC แล้ว เรายังสามารถใช้วิธีเดียวกันเพื่อดึงไฟล์จาก PVC กลับมายังเครื่อง Local ได้ด้วย

เพียงสลับทิศทางของ `kubectl cp`

```bash
mkdir -p ./backup

kubectl -n <namespace> cp \
  busybox-helper:/data/. \
  ./backup/
```

เท่านี้ไฟล์ภายใน PVC ก็จะถูกคัดลอกกลับมายัง Directory `backup` บนเครื่อง Local

แต่สำหรับการ Backup มีประเด็นที่ต่างจากการ Restore เล็กน้อย คือเราอาจไม่จำเป็นต้อง Scale Down แอปเสมอไป

หากเป็นไฟล์ที่ไม่มีการเปลี่ยนแปลงระหว่างคัดลอก เช่น Static Files การ Backup ขณะแอปทำงานอยู่อาจทำได้ตามปกติ ตราบใดที่ Helper Pod สามารถ Mount PVC ได้

แต่ถ้าเป็นไฟล์ที่แอปกำลังเขียนอยู่ เช่น SQLite Database, Application State หรือไฟล์ที่มีข้อมูลสัมพันธ์กันหลายส่วน การคัดลอกขณะแอปทำงานอาจทำให้ได้ Backup ที่ไม่สอดคล้องกัน

สำหรับกรณีนี้ การหยุดแอปอย่างถูกต้องก่อน Backup จะช่วยลดความเสี่ยงได้

<ChatMessage message="การ Copy ไฟล์ออกจาก PVC ไม่ได้หมายความว่าจะได้ Consistent Backup เสมอไป โดยเฉพาะ Database ควรใช้เครื่องมือ Backup ที่เหมาะสม เช่น pg_dump หรือ pg_basebackup สำหรับ PostgreSQL แทนการ Copy Data Directory ตรง ๆ" avatarKey="blackCat" />

### Cleanup และเปิดแอปกลับ

เมื่อคัดลอกไฟล์และตรวจสอบข้อมูลเรียบร้อยแล้ว ให้ลบ BusyBox เพื่อปล่อย Volume

```bash
kubectl -n <namespace> delete pod busybox-helper
```

หากก่อนหน้านี้มีการ Scale Down แอป ให้ Scale กลับไปยังจำนวน Replicas เดิม

```bash
# ตัวอย่างกรณีเดิมมี 1 Replica
kubectl -n <namespace> scale \
  deploy/<deployment> --replicas=1
```

หลังจากนั้นตรวจสอบว่า Pod ของแอปกลับมาทำงานตามปกติ และสามารถอ่านข้อมูลภายใน PVC ได้

## 2. Copy ไฟล์ระหว่าง PVC

จากตัวอย่างแรก เราใช้ BusyBox เพียงตัวเดียวเพื่อคัดลอกไฟล์ระหว่าง Local กับ PVC

แต่ถ้าเราต้องการย้ายข้อมูลจาก PVC หนึ่งไปยังอีก PVC หนึ่ง โดยไม่ต้องดาวน์โหลดไฟล์ลงเครื่อง Local ก่อนล่ะ?

กรณีนี้เราสามารถสร้าง BusyBox สองตัว โดยให้แต่ละตัว Mount PVC ของตัวเอง จากนั้นใช้ `kubectl exec` ร่วมกับ `tar` เพื่อส่งข้อมูลจาก Pod ต้นทางไปยัง Pod ปลายทาง

### เตรียม PVC ต้นทางและปลายทาง

ก่อนเริ่ม ควรตรวจสอบว่า PVC ทั้งสองอยู่ในสถานะ `Bound`

```bash
kubectl -n <namespace> get pvc
```

สำหรับการย้ายข้อมูลระหว่าง PVC เราควรพิจารณาทั้งสองฝั่ง

- **PVC ต้นทาง:** หากแอปยังเขียนข้อมูลอยู่ระหว่างคัดลอก อาจทำให้ข้อมูลที่ย้ายไปไม่สอดคล้องกัน
- **PVC ปลายทาง:** หากมีแอปใช้งานอยู่ อาจเกิดการเขียนข้อมูลชนกัน หรืออ่านไฟล์ที่ยังคัดลอกไม่เสร็จ

ดังนั้น สำหรับ POC นี้ แนะนำให้ Scale Down แอปที่ใช้งาน PVC ทั้งสองฝั่งก่อนเริ่มคัดลอก

```bash
# หยุดแอปฝั่งต้นทาง
kubectl -n <namespace> scale \
  deploy/<source-deployment> --replicas=0

# หยุดแอปฝั่งปลายทาง
kubectl -n <namespace> scale \
  deploy/<destination-deployment> --replicas=0
```

รอให้ Pod ของทั้งสองแอปหยุดทำงานเรียบร้อยก่อนดำเนินการต่อ หาก PVC ใดไม่ได้ถูกใช้งานอยู่ ก็ไม่จำเป็นต้อง Scale Deployment สำหรับ PVC นั้น

<ChatMessage message="การ Scale Down ทั้งสองฝั่งเป็นแนวทางที่เหมาะกับ POC Migration เพราะช่วยให้ข้อมูลต้นทางหยุดเปลี่ยน และป้องกันแอปปลายทางเข้าถึงไฟล์ระหว่าง Copy แต่ในการใช้งานจริงอาจเลือกวิธีอื่นที่ไม่ต้องหยุดระบบได้ หากรองรับ Consistent Snapshot หรือ Online Migration" avatarKey="blackCat" />

### สร้าง BusyBox สองตัว

สร้างไฟล์ `volume-copy-helper.yaml` โดยกำหนด PVC ต้นทางและปลายทางให้กับ BusyBox แต่ละตัว

ในตัวอย่างนี้จะใช้ `busybox-a` เป็นฝั่งต้นทาง และ `busybox-b` เป็นฝั่งปลายทาง

```yaml
# volume-copy-helper.yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox-a
  namespace: <namespace>
  labels:
    app: volume-copy-helper
spec:
  restartPolicy: Never
  containers:
    - name: busybox
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
          readOnly: true
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: <pvc-a>
        readOnly: true
---
apiVersion: v1
kind: Pod
metadata:
  name: busybox-b
  namespace: <namespace>
  labels:
    app: volume-copy-helper
spec:
  restartPolicy: Never
  containers:
    - name: busybox
      image: busybox:1.36
      command: ["sleep", "3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: <pvc-b>
```


PVC ทั้งสองต้องอยู่ใน Namespace เดียวกับ Pod ที่ Mount และในตัวอย่างนี้เรากำหนดให้ PVC ต้นทางเป็น Read-Only เพื่อลดความเสี่ยงจากการแก้ไขข้อมูลโดยไม่ตั้งใจ

Apply Manifest แล้วรอจนทั้งสอง Pod พร้อมใช้งาน

```bash
kubectl apply -f volume-copy-helper.yaml

kubectl -n <namespace> wait \
  --for=condition=Ready \
  pod/busybox-a \
  --timeout=60s

kubectl -n <namespace> wait \
  --for=condition=Ready \
  pod/busybox-b \
  --timeout=60s
```

ก่อนคัดลอก ลองตรวจสอบไฟล์ภายใน PVC ทั้งสองฝั่ง

```bash
# PVC ต้นทาง
kubectl -n <namespace> exec busybox-a -- ls -la /data

# PVC ปลายทาง
kubectl -n <namespace> exec busybox-b -- ls -la /data
```

### คัดลอกไฟล์จาก PVC A ไป PVC B

สำหรับการคัดลอกข้อมูลระหว่าง Pod เราสามารถใช้ `tar` ร่วมกับ Pipe เพื่อส่งข้อมูลจากต้นทางไปยังปลายทางได้โดยไม่ต้องสร้างไฟล์ชั่วคราวบนเครื่อง Local

```bash
set -o pipefail

kubectl -n <namespace> exec busybox-a -- \
  tar cf - -C /data . \
  | kubectl -n <namespace> exec -i busybox-b -- \
  tar xf - -C /data
```

คำสั่งนี้แบ่งการทำงานออกเป็นสองส่วน

- `tar cf - -C /data .` อ่านไฟล์ทั้งหมดจาก `/data` ของ BusyBox A แล้วส่งออกผ่าน Standard Output
- `tar xf - -C /data` รับข้อมูลผ่าน Standard Input แล้วแตกไฟล์ลง `/data` ของ BusyBox B

ส่วน `set -o pipefail` ช่วยให้ตรวจพบความล้มเหลวของคำสั่งฝั่งต้นทางได้ด้วย เมื่อใช้ Shell ที่รองรับ เช่น Bash

ข้อมูลจะถูก Stream ผ่านเครื่องที่รัน `kubectl` โดยไม่จำเป็นต้องจัดเก็บไฟล์ไว้บน Disk ของเครื่องนั้นก่อน

หลังจากคัดลอกเสร็จ ตรวจสอบไฟล์ภายใน PVC ปลายทางอีกครั้ง

```bash
kubectl -n <namespace> exec busybox-b -- ls -la /data
```

### Cleanup และเปิดแอปกลับ

หลังจากตรวจสอบว่าข้อมูลถูกคัดลอกเรียบร้อยแล้ว ให้ลบ BusyBox ทั้งสองตัวเพื่อปล่อย Volume

```bash
kubectl -n <namespace> delete pod busybox-a busybox-b
```

จากนั้น Scale แอปกลับไปยังจำนวน Replicas เดิม โดยตัวอย่างนี้สมมติว่าทั้งสองแอปมีอย่างละ 1 Replica

```bash
kubectl -n <namespace> scale \
  deploy/<source-deployment> --replicas=1

kubectl -n <namespace> scale \
  deploy/<destination-deployment> --replicas=1
```

หากเป็นการ Migration ที่ต้องการย้ายข้อมูลไปใช้ PVC ใหม่แทน PVC เดิม อาจไม่จำเป็นต้องเปิดแอปต้นทางกลับขึ้นมา ทั้งนี้ขึ้นอยู่กับแผนการย้ายระบบ

## จัดการ Permission หลังคัดลอก

อีกเรื่องที่ไม่ควรมองข้ามคือ Permission ของไฟล์

เมื่อคัดลอกไฟล์ผ่าน BusyBox ซึ่งปกติรันด้วย Root ไฟล์ที่ถูกสร้างขึ้นอาจมี Owner เป็น `root` แทน User ที่แอปพลิเคชันใช้งานจริง

หากแอปทำงานด้วย UID อื่น เช่น `1000` อาจพบปัญหา `Permission denied` หรือ `EACCES` เมื่อเปิดแอปกลับขึ้นมา

เราสามารถเปลี่ยน Owner ของไฟล์ภายใน PVC ให้ตรงกับ User ของแอปได้

สำหรับกรณี Local to PVC

```bash
kubectl -n <namespace> exec busybox-helper -- \
  chown -R <uid>:<gid> /data
```

สำหรับกรณี PVC to PVC ให้รันคำสั่งกับ `busybox-b` ซึ่งเป็นฝั่งปลายทางแทน

```bash
kubectl -n <namespace> exec busybox-b -- \
  chown -R <uid>:<gid> /data
```

จากนั้นตรวจสอบ Owner ของไฟล์อีกครั้ง

```bash
kubectl -n <namespace> exec busybox-b -- ls -la /data
```

ค่า UID และ GID ควรอ้างอิงจาก `securityContext.runAsUser`, `runAsGroup` หรือเอกสารของ Container Image ที่แอปใช้งาน และต้องแน่ใจว่า Volume รองรับการเปลี่ยน Ownership

ควรดำเนินการขั้นตอนนี้หลังคัดลอกไฟล์เสร็จ แต่ก่อนลบ Helper Pod และ Scale แอปกลับ โดยไม่จำเป็นต้องเปลี่ยน Owner ของทุกไฟล์หาก Permission เดิมถูกต้องอยู่แล้ว

## ข้อควรระวังสำหรับ Production

แม้ว่าการใช้ BusyBox เป็น Helper Pod จะสะดวกสำหรับการจัดการไฟล์ภายใน PVC แต่ก่อนนำไปใช้กับระบบจริงยังมีเรื่องที่ควรพิจารณาเพิ่มเติม

**Data Consistency**

การหยุดแอปก่อน Copy ช่วยลดความเสี่ยงจากการเปลี่ยนแปลงข้อมูลระหว่างคัดลอก แต่ควรแน่ใจว่าแอปหยุดทำงานอย่างถูกต้อง และไม่มี Process อื่นเขียนข้อมูลลง Volume

โดยเฉพาะ Database ควรใช้เครื่องมือ Backup หรือ Migration ที่รองรับข้อมูลประเภทนั้นโดยตรง

**Storage และ Access Mode**

PVC แบบ RWO อาจไม่สามารถ Mount จากหลาย Node พร้อมกันได้ หาก Helper Pod ไม่สามารถเริ่มทำงาน ควรตรวจสอบ Pod Events และสถานะ Volume ก่อน

**GitOps และ Autoscaling**

หาก Deployment ถูกจัดการด้วย ArgoCD หรือมี HPA ควบคุมจำนวน Replicas การ Scale Down ด้วย `kubectl` อาจถูกระบบปรับกลับโดยอัตโนมัติ

ควรวางแผน Maintenance และจัดการ Reconciliation หรือ Autoscaling ให้เหมาะสมก่อนเริ่มทดลอง

**Permission และ Ownership**

หลังคัดลอกข้อมูล ควรตรวจสอบว่าแอปสามารถอ่านและเขียนไฟล์ได้ตามปกติ โดยเฉพาะกรณีที่ Container ไม่ได้รันด้วย Root

<ChatMessage message="BusyBox ในบทความนี้เป็นเพียง Helper Pod สำหรับทดลอง POC เท่านั้น เมื่อใช้งานเสร็จควรลบทิ้ง ไม่ควรปล่อย Pod ที่รัน sleep ค้างไว้ใน Production โดยไม่จำเป็น" avatarKey="whiteCat" />

## สรุป

การใช้ BusyBox เป็น Helper Pod ช่วยให้เราสามารถเข้าถึงและจัดการไฟล์ภายใน PVC ได้โดยไม่จำเป็นต้องแก้ไข Container Image หรือ Deployment ของแอปพลิเคชัน

| กรณี | Helper Pod | คำสั่งหลัก | Scale Down |
|------|------------|------------|------------|
| Local → PVC | 1 Pod | `kubectl cp` | แนะนำสำหรับ Restore |
| PVC → Local | 1 Pod | `kubectl cp` | ขึ้นอยู่กับข้อมูล |
| PVC → PVC | 2 Pods | `kubectl exec` + `tar` pipe | แนะนำสำหรับ Migration |

สำหรับ POC ที่ต้องการ Restore หรือย้ายข้อมูล การใช้ Flow แบบ Scale Down → Mount PVC → Copy → ตรวจสอบข้อมูล → Cleanup → Scale Up เป็นแนวทางที่เข้าใจง่ายและช่วยลดความเสี่ยงจากการเขียนข้อมูลพร้อมกัน

อย่างไรก็ตาม การ Scale Down ไม่ใช่ข้อบังคับสำหรับทุกกรณี และไม่ได้รับประกันความถูกต้องของ Backup โดยอัตโนมัติ สิ่งสำคัญคือการเลือกวิธีคัดลอกข้อมูลให้เหมาะกับ Workload และลักษณะของข้อมูลที่จัดเก็บอยู่ใน PVC
