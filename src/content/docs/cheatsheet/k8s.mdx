ระบบจัดการ container orchestration ที่ช่วยให้จัดการ container หลายตัวใน cluster ได้อย่างมีประสิทธิภาพ รองรับการ scale, deploy, และ manage applications อัตโนมัติ

## Resource Creation Snippets

สร้าง resource จาก YAML ด้วย `kubectl apply` โดยแต่ละ snippet สามารถแยกเป็นไฟล์แล้วนำไปใช้ได้ทันที

### Pod

Pod เหมาะสำหรับการทดลองหรือ workload ที่ไม่ต้องการ rolling update และ self-healing แบบ Deployment

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80
```

```bash
# สร้าง Pod
kubectl apply -f pod.yaml

# ตรวจสอบ Pod และดูรายละเอียด
kubectl get pod nginx-pod
kubectl describe pod nginx-pod

# ลบ Pod
kubectl delete -f pod.yaml
```

### Deployment

Deployment เหมาะสำหรับ application ที่ต้องการ replicas, rolling update และ self-healing

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80
```

```bash
# สร้างหรืออัปเดต Deployment
kubectl apply -f deployment.yaml

# รอให้ rollout เสร็จ
kubectl rollout status deployment/nginx

# ตรวจสอบ Pods ที่ Deployment ดูแล
kubectl get deployment,pods -l app=nginx

# ลบ Deployment
kubectl delete -f deployment.yaml
```

### Service

Service ใช้เปิด endpoint ให้ Pod อื่นหรือผู้ใช้งานเข้าถึง โดย `selector` ต้องตรงกับ label ของ Pod

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  type: ClusterIP
  selector:
    app: nginx
  ports:
    - name: http
      port: 80
      targetPort: 80
```

```bash
# สร้าง Service
kubectl apply -f service.yaml

# ตรวจสอบ Service และ endpoints
kubectl get svc nginx
kubectl get endpoints nginx

# ทดสอบจากเครื่อง local
kubectl port-forward svc/nginx 8080:80

# ลบ Service
kubectl delete -f service.yaml
```

เปลี่ยน `type` เป็น `NodePort` สำหรับเปิดผ่าน port ของ Node หรือ `LoadBalancer` สำหรับ cloud provider ที่รองรับ

### ConfigMap

ใช้เก็บ configuration ที่ไม่เป็นความลับ และนำไปใช้เป็น environment variables หรือ file ได้

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  app.properties: |
    feature.new-ui=true
    http.timeout=30s
```

```bash
# สร้าง ConfigMap
kubectl apply -f configmap.yaml

# ตรวจสอบค่าใน ConfigMap
kubectl get configmap app-config -o yaml

# ลบ ConfigMap
kubectl delete -f configmap.yaml
```

### Secret

ใช้เก็บข้อมูล sensitive เช่น password, token หรือ API key โดยใช้ `stringData` เพื่อให้เขียนค่า plain text ใน manifest ได้ง่าย

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
type: Opaque
stringData:
  DATABASE_USER: app
  DATABASE_PASSWORD: change-me
  API_TOKEN: replace-me
```

```bash
# สร้าง Secret
kubectl apply -f secret.yaml

# ตรวจสอบ metadata โดยไม่แสดงค่า secret
kubectl get secret app-secret

# อ่านค่าและ decode เฉพาะ key ที่ต้องการ
kubectl get secret app-secret -o jsonpath='{.data.DATABASE_PASSWORD}' | base64 -d

# ลบ Secret
kubectl delete -f secret.yaml
```

> `Secret` ที่เก็บใน Kubernetes เป็น Base64 encoding ไม่ใช่ encryption โดยอัตโนมัติ หลีกเลี่ยงการ commit ค่า secret จริงลง Git

### Volume ใน Pod

ตัวอย่างด้านล่างเป็น snippets ที่พบบ่อยสำหรับเพิ่ม `volume` และ `volumeMounts` ใน `spec` ของ Pod หรือ Deployment template

#### `emptyDir` สำหรับ temporary storage

ข้อมูลอยู่ตลอดอายุของ Pod และจะหายเมื่อ Pod ถูกลบหรือย้ายไป Node ใหม่

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  containers:
    - name: app
      image: nginx:1.27
      volumeMounts:
        - name: cache
          mountPath: /var/cache/app
  volumes:
    - name: cache
      emptyDir: {}
```

#### `emptyDir` แบบใช้ memory

เหมาะกับ cache ชั่วคราวที่ต้องการความเร็ว แต่ใช้ RAM ของ Node และควรกำหนดขนาดจำกัด

```yaml
volumes:
  - name: memory-cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi
```

#### `hostPath` สำหรับ mount directory จาก Node

ใช้เฉพาะกรณีที่จำเป็นจริง ๆ เพราะ Pod จะผูกกับ filesystem ของ Node และอาจมีปัญหาเมื่อย้าย Node

```yaml
volumes:
  - name: node-data
    hostPath:
      path: /var/lib/my-app
      type: DirectoryOrCreate
```

#### Mount ConfigMap เป็น file

```yaml
volumes:
  - name: app-config
    configMap:
      name: app-config
      items:
        - key: app.properties
          path: app.properties
```

```yaml
volumeMounts:
  - name: app-config
    mountPath: /etc/my-app/app.properties
    subPath: app.properties
    readOnly: true
```

#### Mount Secret เป็น file

```yaml
volumes:
  - name: app-secret
    secret:
      secretName: app-secret
      defaultMode: 0400
```

```yaml
volumeMounts:
  - name: app-secret
    mountPath: /etc/my-app/secrets
    readOnly: true
```

#### ใช้ PVC เป็น persistent storage

PVC เป็นวิธีมาตรฐานสำหรับขอ storage ที่ยังอยู่แม้ Pod ถูกสร้างใหม่ โดย `storageClassName` ต้องตรงกับ StorageClass ใน cluster

แบบทั่วไปให้ใช้ PVC ขอ storage จาก StorageClass ที่มีอยู่ใน cluster:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: standard
  resources:
    requests:
      storage: 1Gi
```

ถ้า cluster ไม่มี dynamic provisioning สามารถสร้าง PV เองแล้วให้ PVC bind ด้วย `storageClassName` และขนาดที่ตรงกันได้:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: app-data-pv
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  hostPath:
    path: /mnt/data/app
```

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: manual
  resources:
    requests:
      storage: 1Gi
```

> `hostPath` เหมาะกับ local cluster หรือ lab เท่านั้น สำหรับ production ควรใช้ StorageClass และ CSI driver ของ cloud หรือ storage platform

```yaml
volumeMounts:
  - name: app-data
    mountPath: /var/lib/my-app

volumes:
  - name: app-data
    persistentVolumeClaim:
      claimName: app-data
```

```bash
# สร้าง PVC
kubectl apply -f pvc.yaml

# ตรวจสอบสถานะ PVC และ PV ที่ถูก bind
kubectl get pvc,pv

# ลบ PVC เมื่อไม่ต้องการใช้แล้ว
kubectl delete -f pvc.yaml
```

#### Mount เฉพาะ file ด้วย `subPath`

ใช้เมื่อต้องการ mount key เดียวจาก ConfigMap หรือ Secret โดยไม่ทับทั้ง directory

```yaml
volumeMounts:
  - name: app-config
    mountPath: /etc/my-app/app.properties
    subPath: app.properties
    readOnly: true
```

> File ที่ mount ด้วย `subPath` จะไม่รับการ update จาก ConfigMap หรือ Secret โดยอัตโนมัติ ต้อง restart Pod หลังแก้ค่า

#### รวมหลาย source ด้วย `projected`

รวม ConfigMap, Secret และ Downward API ไว้ใน directory เดียว

```yaml
volumes:
  - name: runtime-config
    projected:
      sources:
        - configMap:
            name: app-config
        - secret:
            name: app-secret
        - downwardAPI:
            items:
              - path: pod-name
                fieldRef:
                  fieldPath: metadata.name
```

ตัวอย่างการนำ volume ไปใช้ใน Deployment:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app
  template:
    metadata:
      labels:
        app: app
    spec:
      containers:
        - name: app
          image: nginx:1.27
          volumeMounts:
            - name: runtime-config
              mountPath: /etc/my-app
              readOnly: true
      volumes:
        - name: runtime-config
          projected:
            sources:
              - configMap:
                  name: app-config
              - secret:
                  name: app-secret
```

```bash
# ตรวจสอบ volume mount จากใน container
kubectl exec deploy/app -- ls -la /etc/my-app

# ดูรายละเอียด volume และ mount configuration
kubectl describe pod -l app=app
```

## Pod

Pod คือ smallest deployable unit ใน Kubernetes โดยแต่ละ Pod จะ contain หนึ่งหรือหลาย containers ที่ใช้ shared storage และ network

```bash
# แสดง pods ทั้งหมดใน namespace ปัจจุบัน
kubectl get pods

# แสดง pods พร้อม detail เพิ่มเติม
kubectl get pods -o wide

# แสดง pods ทั้งหมดในทุก namespace
kubectl get pods --all-namespaces

# ดูข้อมูล detail ของ pod
kubectl describe pod <pod-name>

# ดู logs ของ pod
kubectl logs <pod-name>

# ดู logs แบบ follow
kubectl logs -f <pod-name>

# exec เข้าไปใน container
kubectl exec -it <pod-name> -- /bin/sh

# ลบ pod
kubectl delete pod <pod-name>
```

## Deployment

Deployment คือ abstraction layer ที่อยู่บน Pod ช่วยให้จัดการ scaling, rolling updates, และ rollback ได้ง่ายขึ้น

```bash
# แสดง deployments ทั้งหมด
kubectl get deployments

# ดูข้อมูล detail ของ deployment
kubectl describe deployment <deployment-name>

# สร้าง deployment จาก yaml file
kubectl apply -f <deployment.yaml>

# ดู rollout status
kubectl rollout status deployment/<deployment-name>

# rollback deployment กลับไป version ก่อนหน้า
kubectl rollout undo deployment/<deployment-name>

# ดู history ของ rollout
kubectl rollout history deployment/<deployment-name>
```

## Scaling

```bash
# scale deployment ไปที่จำนวน replicas ที่ต้องการ
kubectl scale deployment <deployment-name> --replicas=3

# scale แบบ horizontal pod autoscaler
kubectl autoscale deployment <deployment-name> --min=2 --max=10 --cpu-percent=80
```

## Services

Service คือ abstraction ที่ defines logical set of pods และ policy สำหรับเข้าถึง pods นั้นๆ

```bash
# แสดง services ทั้งหมด
kubectl get services
kubectl get svc

# ดูข้อมูล detail ของ service
kubectl describe service <service-name>

# สร้าง service แบบ LoadBalancer
kubectl expose deployment <deployment-name> --port=80 --type=LoadBalancer

# สร้าง service แบบ ClusterIP (internal)
kubectl expose deployment <deployment-name> --port=80 --type=ClusterIP

# สร้าง service แบบ NodePort
kubectl expose deployment <deployment-name> --port=80 --type=NodePort
```

### Port Forwarding

```bash
# forward port จาก local ไปยัง pod
kubectl port-forward pod/<pod-name> 8080:80

# forward port จาก local ไปยัง service

```

## ConfigMaps

ConfigMap ใช้เก็บ configuration ที่ไม่เป็น secret เช่น environment variables, command-line arguments, config files

```bash
# สร้าง configmap จาก literal
kubectl create configmap <configmap-name> --from-literal=key=value

# สร้าง configmap จาก file
kubectl create configmap <configmap-name> --from-file=<file-path>

# สร้าง configmap จาก env file
kubectl create configmap <configmap-name> --from-env-file=<env-file-path>

# ดู configmap
kubectl get configmaps
kubectl describe configmap <configmap-name>
```

## Secrets

Secret ใช้เก็บข้อมูลที่ sensitive เช่น passwords, tokens, keys

```bash
# สร้าง secret จาก literal
kubectl create secret generic <secret-name> --from-literal=key=value

# สร้าง secret จาก file
kubectl create secret generic <secret-name> --from-file=<file-path>

# สร้าง secret แบบ docker registry
kubectl create secret docker-registry <secret-name> --docker-server=<server> --docker-username=<user> --docker-password=<pass>

# ดู secrets
kubectl get secrets

# ดู secret value (base64 decode)
kubectl get secret <secret-name> -o jsonpath='{.data.key}' | base64 -d
```

## Namespaces

Namespace ช่วยให้แบ่ง cluster ออกเป็นหลาย virtual clusters


## Logging & Debugging

```bash

kubectl get pods | grep -v Running

# ดู logs ของ pod ที่มีหลาย containers
```

## Resources

## YAML Operations

```bash
# แสดง yaml ของ resource (ไม่ apply)
kubectl get pod <pod-name> -o yaml

# สร้าง resource จาก yaml
kubectl apply -f <file.yaml>

# สร้างหลาย resources จาก directory
kubectl apply -f <directory>/

# ลบ resource จาก yaml
kubectl delete -f <file.yaml>

# ดู difference ก่อน apply
kubectl diff -f <file.yaml>
```

## Common Options

```bash
# -n : ระบุ namespace
kubectl get pods -n <namespace>

# -o : กำหนด output format (yaml, json, wide)
kubectl get pods -o yaml
kubectl get pods -o json
kubectl get pods -o wide

# -l : filter ด้วย label
kubectl get pods -l app=myapp

# -f : ระบุ filename
kubectl apply -f deployment.yaml

# --dry-run : ทดสอบคำสั่งโดยไม่ apply
kubectl apply -f deployment.yaml --dry-run

# -w : watch mode
kubectl get pods -w
```
